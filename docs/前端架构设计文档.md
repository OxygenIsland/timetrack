# 🎨 前端模块设计文档（一期 / 单人版）

> **设计目标**：UI 与业务分离、模块解耦、可插拔、可拓展。
> **设计原则**：参考行业成熟方案（领域驱动设计 DDD + 插件化架构 + 微内核模式），避免单人项目常见的"组件地狱"和"业务逻辑散落各处"。
> **关联文档**：`前端需求-核心需求.md`、`后端架构设计文档.md`、`错误码体系规范.md`、`技术路线设计文档.md`

---

## 一、设计原则（先讲原则，再讲模块）

| 原则 | 含义 | 为什么重要 |
|------|------|-----------|
| **UI 与业务分离** | UI 组件只负责渲染，业务逻辑在 store / service / hook 中 | 单人项目最容易把业务逻辑塞进组件，导致改一个 UI 要全量测试 |
| **单向数据流** | 事件流：`Page → Container → UI Component → Store → Service → API` | 避免双向耦合，可追溯 |
| **约定优于配置** | 目录结构、命名、注册方式严格统一 | 单人维护，不靠"记忆"靠"约定" |
| **可插拔** | 每个业务模块都是"插件"，可独立注册/卸载 | 后续加 M5/M6 不改框架 |
| **接口契约** | 模块之间通过"接口"通信，不直接依赖实现 | 替换实现不影响调用方 |
| **错误码统一** | 所有错误走 `错误码体系规范.md` 定义的错误码 | 出问题能定位 |
| **类型先行** | TypeScript Strict + 接口定义先于实现 | 单人项目最大的效率提升 |

## 二、行业参考方案

设计参考了以下行业主流模式：

| 模式 | 来源 | 应用到本项目 |
|------|------|-------------|
| **领域驱动设计 (DDD)** | Eric Evans《领域驱动设计》 | 按业务领域划分模块边界（M1 看板、M2 记录、M3 工时、M4 报表） |
| **微内核架构 (Microkernel)** | Linux kernel、Eclipse、VSCode | 核心框架 + 业务插件，所有业务模块都是"插件" |
| **微前端 (Module Federation)** | Webpack 5、single-spa | 模块独立打包、独立部署（本期不上，二期预留） |
| **插件化架构** | VSCode、Chrome Extension、Element Plus 组件注册 | 模块通过 `registerModule()` 注入，框架不关心模块实现 |
| **Presentational/Container Components** | Dan Abramov | UI 组件只负责渲染，Container 负责业务 |
| **Hooks 模式** | React 官方 | 业务逻辑封装为自定义 Hook，可复用、可测试 |
| **Pinia/Zustand Store Pattern** | Vue / React 生态 | 状态管理按域划分（personnel、workhour、report...） |

## 三、整体架构（分层 + 模块化）

### 3.1 整体分层

```
┌────────────────────────────────────────────────────────────┐
│  L1 入口层（Entry Layer）                                  │
│     - Electron 主进程                                       │
│     - React 应用入口（main.tsx）                            │
│     - 路由根（AppRouter）                                   │
├────────────────────────────────────────────────────────────┤
│  L2 模块注册层（Module Registry Layer）⭐ 微内核             │
│     - 模块注册中心（ModuleRegistry）                        │
│     - 模块生命周期管理（onMount / onUnmount）                │
│     - 模块间通信总线（EventBus）                            │
├────────────────────────────────────────────────────────────┤
│  L3 业务模块层（Business Modules Layer）                     │
│     - M1 看板模块（dashboard）                              │
│     - M2 人员记录模块（records）                            │
│     - M3 工时模块（workhour）                               │
│     - M4 报表模块（report）                                 │
│     - 系统模块（system）                                    │
├────────────────────────────────────────────────────────────┤
│  L4 业务能力层（Capabilities / Services Layer）             │
│     - API 客户端（apiClient）                               │
│     - 错误处理（errorHandler）                              │
│     - WebSocket 管理（wsManager）                           │
│     - 鉴权（auth）                                          │
├────────────────────────────────────────────────────────────┤
│  L5 UI 组件库层（UI Components Layer）                       │
│     - 通用组件（Common Components）                          │
│     - 业务组件（Domain Components）                          │
│     - 第三方 UI 库（AntD、shadcn）                          │
├────────────────────────────────────────────────────────────┤
│  L6 基础设施层（Infrastructure Layer）                      │
│     - 工具函数（utils）                                     │
│     - 常量（constants）                                     │
│     - 类型定义（types）                                     │
│     - 配置（config）                                        │
└────────────────────────────────────────────────────────────┘
```

**依赖方向**：上层 → 下层，单向无循环。

### 3.2 与后端的边界

| 前端职责 | 后端职责 |
|---------|---------|
| 渲染 UI、收集用户输入 | 业务规则计算 |
| 调用 API、订阅 WebSocket | 数据持久化 |
| 错误码展示（用户层） | 错误码定义（系统层） |
| 客户端缓存（TanStack Query） | 业务逻辑 |
| 路由、模块注册 | 模块编排 |
| UI 状态管理（Zustand） | - |

## 四、模块注册机制 ⭐ 微内核核心

### 4.1 为什么需要模块注册机制

**问题**：传统的 `import` 方式导致模块之间耦合严重：

```typescript
// ❌ 反例：硬编码依赖
import { DashboardPage } from '@/modules/dashboard/DashboardPage';
import { RecordsPage } from '@/modules/records/RecordsPage';
// 每加一个模块都要改这里
```

**解决方案**：模块通过注册中心注入，框架不关心模块内部实现：

```typescript
// ✅ 正例：注册式
import { moduleRegistry } from '@/core/registry';

moduleRegistry.register({
  id: 'dashboard',
  name: '看板',
  routes: [{ path: '/dashboard', component: DashboardPage }],
  navigation: { icon: 'DashboardOutlined', order: 1 },
});

// 加新模块只需注册一次
```

```typescript
export interface IModule {

  /** 模块提供的路由（可能多个） */
  routes: IModuleRoute[];
  
  /** 模块在导航栏的入口（可选） */
  navigation?: IModuleNavigation;
  
  /** 模块提供的权限点（用于权限系统） */
  permissions?: string[];
  
  /** 模块依赖的其他模块 id（可选） */
  dependencies?: string[];
  
  /** 模块对外暴露的能力（其他模块可调用） */
  capabilities?: Record<string, Function>;
}

  /** 路由路径 */
  path: string;
  /** 路由组件（Container 组件） */
  component: React.ComponentType<any>;
  /** 子路由 */
  children?: IModuleRoute[];
  /** 是否需要鉴权 */
  requireAuth?: boolean;
  /** 需要的权限点 */
  permissions?: string[];
  /** 路由 meta 信息 */
  meta?: {
    title?: string;
    icon?: string;
    hideInMenu?: boolean;
    [key: string]: any;
  };
}

export interface IModuleNavigation {
  /** 菜单标题 */
  title: string;
  /** 菜单图标 */
  icon?: string;
  /** 排序（越小越靠前） */
  order?: number;

  parent?: string;
}

export interface ModuleContext {
  /** 当前用户信息 */

  /** API 客户端 */
  api: IApiClient;
```

### 4.3 模块注册中心

```typescript
// src/core/registry/ModuleRegistry.ts

import { IModule } from './types';

class ModuleRegistry {
  private modules = new Map<string, IModule>();
  private mounted = new Set<string>();

  /**
   * 注册模块
   */
  register(module: IModule): void {
    if (this.modules.has(module.id)) {
      console.warn(`[ModuleRegistry] 模块 ${module.id} 已存在，将被覆盖`);
    }
    this.modules.set(module.id, module);
    console.info(`[ModuleRegistry] 注册模块: ${module.id}@${module.version}`);
  }

  /**
   * 批量注册
   */
  registerAll(modules: IModule[]): void {
    modules.forEach((m) => this.register(m));
  }

  /**
   * 挂载模块（按依赖顺序）
   */
  async mountAll(ctx: ModuleContext): Promise<void> {
    // 拓扑排序：先挂载无依赖的
    const sorted = this.topoSort();
    for (const mod of sorted) {
      await this.mount(mod, ctx);
    }
  }

  /**
   * 挂载单个模块
   */
  async mount(id: string, ctx: ModuleContext): Promise<void> {
    const mod = this.modules.get(id);
    if (!mod) throw new Error(`模块不存在: ${id}`);
    if (this.mounted.has(id)) return;

    // 先挂载依赖
    if (mod.dependencies) {
      for (const dep of mod.dependencies) {
        await this.mount(dep, ctx);
      }
    }

    if (mod.onMount) {
      await mod.onMount(ctx);
    }
    this.mounted.add(id);
  }

  /**
   * 卸载模块
   */
  async unmount(id: string): Promise<void> {
    const mod = this.modules.get(id);
    if (!mod || !this.mounted.has(id)) return;
    if (mod.onUnmount) {
      await mod.onUnmount({} as ModuleContext);
    }
    this.mounted.delete(id);
  }

  /**
   * 获取模块
   */
  get(id: string): IModule | undefined {
    return this.modules.get(id);
  }

  /**
   * 获取所有路由（按 order 排序）
   */
  getAllRoutes(): IModuleRoute[] {
    const allRoutes: IModuleRoute[] = [];
    this.modules.forEach((m) => {
      allRoutes.push(...m.routes);
    });
    return allRoutes;
  }

  /**
   * 获取所有导航菜单
   */
  getAllNavigation(): Array<IModuleNavigation & { id: string; path: string }> {
    const navs: Array<IModuleNavigation & { id: string; path: string }> = [];
    this.modules.forEach((m) => {
      if (m.navigation) {
        const mainRoute = m.routes[0];
        navs.push({
          id: m.id,
          path: mainRoute?.path || '/',
          ...m.navigation,
        });
      }
    });
    return navs.sort((a, b) => (a.order || 999) - (b.order || 999));
  }

  /**
   * 拓扑排序（按依赖关系）
   */
  private topoSort(): string[] {
    const visited = new Set<string>();
    const result: string[] = [];
    
    const dfs = (id: string) => {
      if (visited.has(id)) return;
      visited.add(id);
      const mod = this.modules.get(id);
      if (mod?.dependencies) {
        mod.dependencies.forEach((dep) => {
          if (!this.modules.has(dep)) {
            throw new Error(`模块 ${id} 依赖的 ${dep} 不存在`);
          }
          dfs(dep);
        });
      }
      result.push(id);
    };
    
    this.modules.forEach((_, id) => dfs(id));
    return result;
  }
}

export const moduleRegistry = new ModuleRegistry();
```

```typescript
import { apiClient, wsManager, eventBus, globalStore } from '@/core';

  <AppRouter routes={allRoutes} />,
  document.getElementById('root')
);
```

### 5.2 三层分离原则 ⭐

| 层 | 职责 | 不能做 |
|----|------|--------|
| **pages/** | 路由入口、组合 containers | ❌ 写业务逻辑、❌ 直接调 API |
| **containers/** | 业务逻辑、状态管理、数据流编排 | ❌ 写 UI（div/span/antd 组件） |
| **components/** | 纯 UI 渲染 | ❌ 调 API、❌ 读 store、❌ 处理业务逻辑 |

**示例对比**：

```typescript
// ❌ 反例：UI 组件里写业务逻辑
function WorkHourTable({ data }) {
  const [filtered, setFiltered] = useState([]);
  
  useEffect(() => {
    // 业务逻辑散落在 UI 里
    const result = data.filter(d => d.valid_seconds > 300);
    setFiltered(result);
  }, [data]);
  
  return <Table dataSource={filtered} />;
}

// ✅ 正例：UI 组件纯渲染，Container 处理业务
// components/WorkHourTable.tsx
function WorkHourTable({ data }: { data: WorkHourRecord[] }) {
  return <Table dataSource={data} columns={columns} />;
}

// containers/WorkHourRecordContainer.tsx
function WorkHourRecordContainer() {
  const records = useWorkHourRecords();  // Hook 处理业务
  const filtered = records.filter(r => r.valid_seconds > 300);
  return <WorkHourTable data={filtered} />;
}
```

## 六、业务能力层（Capabilities）⭐ 解耦关键

### 6.1 为什么需要业务能力层

**问题**：模块之间互相调用会形成耦合：

```typescript
// ❌ 反例：模块间直接依赖
import { useWorkHourStore } from '@/modules/workhour/stores';

function DashboardPage() {
  const workHour = useWorkHourStore();  // 看板模块依赖了工时模块
  // ...
}
```

**解决方案**：模块通过"能力（capability）"暴露能力，其他模块通过 `ctx.capabilities` 调用，不直接依赖：

```typescript
// ✅ 正例：通过能力调用
// 工时模块在 onMount 中注册能力
moduleRegistry.register({
  id: 'workhour',
  capabilities: {
    getRealtimeWorkHour: async (globalId: string) => { ... },
    getTodayWorkHour: async (globalId: string) => { ... },
  },
});

// 看板模块通过 ctx 调用
function DashboardPage() {
  const ctx = useModuleContext();
  const workHour = await ctx.capabilities.workhour?.getRealtimeWorkHour(id);
  // ...
}
```

```typescript
class ApiClient {
  async get<T>(url: string, params?: any): Promise<T> {
    const res = await fetch(url, { method: 'GET', params });
    return this.handleResponse(res);
  }
  
  async post<T>(url: string, body?: any): Promise<T> {
    const res = await fetch(url, { method: 'POST', body });
    return this.handleResponse(res);
  }
  
  private async handleResponse(res: Response) {
    if (!res.ok) {
      const error = await res.json();
      throw error; // 错误码体系规范的错误
    }
    return res.json();
  }
}

  async getRecords(params: QueryParams) {

  }
```

## 十、模块间通信（EventBus）

### 10.1 何时用 EventBus

- 某个事件需要多个模块响应（如"人员进入"事件，看板要更新、工时要累计）
- 调用方不关心响应方是谁
- 异步通知

### 10.2 EventBus 实现

```typescript
// core/eventBus/EventBus.ts
type EventHandler = (data: any) => void | Promise<void>;

class EventBus {
  private handlers = new Map<string, EventHandler[]>();

  on(event: string, handler: EventHandler): () => void {
    if (!this.handlers.has(event)) {
      this.handlers.set(event, []);
    }
    this.handlers.get(event)!.push(handler);
    
    // 返回取消订阅函数
    return () => {
      this.off(event, handler);
    };
  }

  off(event: string, handler: EventHandler): void {
    const handlers = this.handlers.get(event);
    if (handlers) {
      const idx = handlers.indexOf(handler);
      if (idx > -1) handlers.splice(idx, 1);
    }
  }

  async emit(event: string, data: any): Promise<void> {
    const handlers = this.handlers.get(event) || [];
    await Promise.all(handlers.map((h) => h(data)));
  }
}

export const eventBus = new EventBus();
```

```typescript
    });
```
```typescript
  }

    code: error.code,
    trace_id: error.trace_id,

  });
}
```

## 十五、设计合理性自检 ⭐

### 15.1 ✅ 设计合理之处

| 设计点 | 合理性 |
|--------|--------|
| **UI 与业务三层分离（page/container/component）** | 单人维护也保持边界，避免"组件里写业务" |

| **错误码体系集成** | 前后端统一错误处理 |
| **TypeScript 严格模式** | 单人项目最大的效率提升 |
| **目录结构约定** | 不靠"记忆"，靠"约定" |

### 15.2 ⚠️ 需要警惕的过度设计

| 项 | 风险 | 对策 |
|----|------|------|
| **微内核架构对单人偏重** | 一开始就搭注册中心，工作量偏大 | 一期可先用"硬编码 import"起步，二期再上注册中心（但预留接口） |
| **三层分离（page/container/component）对单人偏重** | 文件数量翻倍 | 简单页面可简化（如只有一个 Container，不强行分 page） |
| **Capabilities 模式可能过度抽象** | 一期模块少，可能"为解耦而解耦" | 一期模块间直接调也接受，二期模块多了再上 capabilities |
| **EventBus 滥用** | 任何事件都走 EventBus 会混乱 | 同一模块内用 store 即可，跨模块才用 EventBus |
| **过度组件化** | 每个小组件都拆文件 | 简单组件合并到容器内，复杂组件再拆 |

### 15.3 单人项目的"刚刚好"建议

**一期推荐方案**（务实版）：

```
✅ 必做：
- UI 与业务三层分离（page/container/component）
- 通用组件与业务组件分离
- TypeScript 严格模式
- 错误码体系集成
- 全局 store + 模块 store 分离

⚠️ 一期可简化（但保留接口）：
- 模块注册机制（先硬编码 import，预留 IModule 接口）
- Capabilities 模式（一期模块直接调，二期多了再抽象）
- EventBus（一期只用 props / store，二期再上 EventBus）

❌ 一期不做：
- Module Federation 微前端
- i18n
- Storybook
```
