# ⚙️ 后端架构设计文档（一期 / 单人版）

> **设计前提**：
> 1. **算法部分由算法工程师负责**——后端不做模型训练/调优，但需要定义"算法侧交付物"与"后端消费方式"之间的**契约层**，做到算法侧独立交付、独立升级、后端零修改接入。
> 2. **日志系统必须完整**——所有模块都有结构化日志 + 本地持久化 + 关键事件留痕（可追溯、可查询）。
> 3. **本期重点是模块划分合理性**，不深入实现细节。
>
> **关联文档**：`前端需求-核心需求.md`、`后端需求-核心需求.md`、`技术路线设计文档.md`

---

## 一、设计原则（先讲原则，再讲模块）

| 原则 | 含义 | 为什么 |
|------|------|--------|
| **算法解耦** | 后端通过标准化契约调用算法侧能力，算法侧作为可替换子系统 | 算法不是你做，必须做到算法侧独立迭代 |
| **单向数据流** | 摄像头 → 算法侧 → 后端业务层 → 前端（无回流） | 避免循环依赖 |
| **分层清晰** | 接入层 / 业务层 / 领域层 / 基础设施层，分层依赖 | 单人维护也要有边界感 |
| **日志一等公民** | 每个模块自带 logger，关键事件必须落本地文件 | 出问题能查、甲方验收能交账 |
| **配置外置** | 摄像头 IP、阈值、规则都在外部配置，不在代码里 | 后续换点位/调参数不动代码 |
| **故障隔离** | 算法挂了不影响看板基础渲染，工时计算挂了不影响数据采集 | 7×24 必须的设计 |

## 三、模块详细设计（重点是边界）

### 3.1 接入层（Edge Layer）

**定位**：所有"外部系统对接"都收敛在这一层，内部业务不直接与外部协议打交道。

#### 模块 3.1.1 摄像头接入适配器

| 项 | 说明 |
|----|------|
| **职责** | 屏蔽摄像头厂商差异（海康 / 大华 / ONVIF），向上提供统一的"摄像头抽象" |
| **核心接口** | `拉流地址`、`云台控制`、`事件订阅`、`设备状态查询` |
| **当前支持** | 海康 ISAPI + ONVIF（设计上预留大华、宇视接口位） |
| **日志** | 连接状态、断线重连、鉴权失败、设备离线告警 |

#### 模块 3.1.2 算法侧接入适配器 ⭐ 重点

| 项 | 说明 |
|----|------|
| **职责** | **算法侧与后端的"翻译官"**，定义算法侧交付物的契约 |
| **设计动机** | 算法不是你做。算法侧可能用 Python 算法包 / 算法 SDK / HTTP 服务 / 消息队列，必须有一个适配层把这些都"屏蔽掉"，让业务层只看到"统一的算法事件流" |
| **核心接口** | `启动算法任务`、`停止算法任务`、`接收算法事件`、`查询算法状态` |
| **日志** | 每次收到算法事件、算法任务启停、算法异常 |

**算法侧交付物契约（草案）**：

> 这是后端与算法侧之间**唯一需要对齐的接口文档**，下版本固化。

| 项 | 内容 |
|----|------|
| **算法侧部署形态** | 与后端同主机（也可独立主机，HTTP/MQTT 通信） |
| **通信协议** | 优先 HTTP + JSON；备选 gRPC / ZeroMQ / Redis Streams |
| **算法侧推送给后端的事件** | 见下表"算法事件 JSON Schema" |
| **后端调用算法侧的能力** | 启动/停止任务、查询算法状态、修改算法参数 |
| **算法侧需要的能力** | 拉流地址、ROI 配置、算法结果落库由谁负责（建议算法侧只推流，结果归后端） |

**算法事件 JSON Schema（草案）**：

```json
{
  "event_id": "uuid",
  "timestamp": "2026-09-05T18:30:15.123+08:00",
  "camera_id": "cam_01",
  "frame_meta": {
    "frame_ts": "2026-09-05T18:30:15.100+08:00",
    "frame_seq": 123456
  },
  "detections": [
    {
      "track_id_local": 17,                          // 单摄像头内跟踪 ID
      "track_id_global": "g_0042",                    // 跨摄像头全局 ID（算法侧给出，或后端算）
      "bbox": [120, 240, 200, 380],
      "confidence": 0.93,
      "personnel_class": "worker",                    // "worker" | "manager"
      "class_confidence": 0.88,
      "zone_id": "tire_position_01",                  // 区域归属
      "reid_feature": "base64-encoded-512-floats"
    }
  ]
}
```

> ⚠️ 这里的关键设计决策：
> - `track_id_global` **应由算法侧给出**（因为跨摄像头 ReID 是算法职责）。
> - `zone_id` 也由算法侧给出（区域映射规则由算法侧维护）。
> - `reid_feature` 是给后端做"二次校验 / 离线分析"用，不是每条事件都需要。

**适配层支持的算法侧形态**（可切换）：

| 形态 | 适配方式 | 何时用 |
|------|---------|--------|
| **A. 算法侧 Python 包（import 方式）** | adapter 内部 `from partner_algo import AlgoService`，调用其 API | 算法侧与后端同主机、同语言 |
| **B. 算法侧 HTTP 服务** | adapter 内部 `httpx.AsyncClient` 调用算法侧 REST API | 算法侧独立部署、跨语言 |
| **C. 算法侧 MQTT/ZMQ 消息推送** | adapter 内部订阅消息队列 | 异步、高吞吐场景 |
| **D. 算法侧只交付"事件文件"** | adapter 启动时 tail 文件 | 算法侧深度集成度低时（兜底） |

> 选 A 还是 B 还是 C **取决于算法侧的交付方式**。后端把 4 种适配方式都实现为可插拔的"驱动"，通过配置切换。

#### 模块 3.1.3 历史录像接入适配器

| 项 | 说明 |
|----|------|
| **职责** | 屏蔽 NVR 厂商差异，提供统一的"按时间查询录像"接口 |
| **核心接口** | `查询录像片段`、`下载录像片段`、`截图` |
| **当前支持** | 海康 SDK（HCNetSDK）；预留 ONVIF Profile G |

#### 模块 3.1.4 本地 IPC（与 Electron 主进程通信）

| 项 | 说明 |
|----|------|
| **职责** | 后端服务与 Electron 主进程之间通信（启动指令、退出信号、心跳） |
| **通信方式** | 优先 HTTP localhost（最简单）；备选 stdin/stdout pipe |
| **无需鉴权** | 同主机通信 |

### 3.2 业务编排层（Orchestration Layer）

**定位**：调度多个领域模块完成业务用例。是后端的"业务流程大脑"。

#### 模块 3.2.1 实时事件编排服务 ⭐ 核心

| 项 | 说明 |
|----|------|
| **职责** | 接收算法事件流 → 转换为业务事件 → 落库 → 推送 WebSocket → 触发工时累计 |
| **核心数据流** | algo_event → validate → dedup → enrich → persist → publish_ws → trigger_workhour |
| **关键决策** | - **去重在哪做**：算法侧已经在跨摄像头层面去重了，但保险起见后端做"业务级去重"（短时间同区域同人员合并）<br>- **丢数据怎么办**：算法事件先入本地队列（落盘），再异步处理（**保证不丢**）<br>- **高峰期怎么办**：背压机制，队列满则丢弃最旧帧 + 告警日志 |
| **日志** | 每条事件处理轨迹、丢弃决策、队列状态、推送失败重试 |

#### 模块 3.2.2 工时计算服务

| 项 | 说明 |
|----|------|
| **职责** | 根据进出事件 + 工时规则 + 班次，实时累计每个人的有效工时 |
| **核心数据流** | event → 找到对应"在场状态" → 应用规则 → 累计工时 → 落库 → 推送前端 |
| **关键决策** | - **状态机**：每个人在每个区域内维护"在场状态机"（在场/离场）<br>- **规则引擎**：规则配置外置，运行时热加载<br>- **历史工时**：可重算（离线 batch），方便修正确认后重新计算 |
| **日志** | 每次工时变化、规则生效、人工修正、计算重跑 |

#### 模块 3.2.3 报表生成服务

| 项 | 说明 |
|----|------|
| **职责** | 根据查询条件，从数据库聚合数据，生成日报/周报/月报，导出 Excel/PDF |
| **核心数据流** | query → 解析 → 查库 → 聚合 → 渲染模板 → 落盘 → 返回下载链接 |
| **关键决策** | - **异步生成**：报表生成任务进入队列，Worker 异步处理，前端轮询/WS 推送进度<br>- **模板化**：报表模板外置（HTML 模板 + 数据替换）<br>- **查询性能**：日/月报涉及大量聚合，必须有数据库索引 + 预聚合表 |
| **日志** | 每次导出任务、耗时、文件大小、失败重试 |

#### 模块 3.2.4 系统监控服务

| 项 | 说明 |
|----|------|
| **职责** | 监控摄像头在线、算法侧心跳、数据库连接、服务进程健康度 |
| **核心数据流** | 定时探测 → 状态汇总 → 状态 API → 推送前端（看板角落状态栏） |
| **关键决策** | - **多级健康度**：正常 / 降级 / 异常<br>- **告警阈值**：可配置（如摄像头离线 30s 告警）<br>- **告警渠道**：一期仅写本地日志 + 看板显示，二期可加邮件/钉钉 |
| **日志** | 状态变化、告警触发、心跳异常 |

### 3.3 领域层（Domain Layer）

**定位**：核心业务对象和业务规则。不依赖任何外部协议或框架。

| 领域模块 | 核心实体 | 关键业务规则 |
|----------|---------|--------------|
| **人员事件领域** | PersonEvent（进出流水） | 事件类型、区域归属、去重规则 |
| **人员档案领域** | Person（全局身份）、PersonnelClass（人员类别） | 人员去重、类别判定 |
| **工时领域** | WorkHourRecord、WorkHourRule、Shift | 有效工时判定、班次时间、规则生效 |
| **区域领域** | Zone（胎位/工件）、CameraZoneMapping | 区域划分、摄像头与区域映射 |
| **配置领域** | Config（各种系统配置） | 版本化、热更新、变更审计 |
| **报表领域** | ReportTask、ReportTemplate | 任务生命周期、模板版本 |

**设计原则**：
- **领域对象不感知数据库**：通过仓储接口（Repository Pattern）访问数据
- **业务规则在领域层**：不在 service 层也不在 controller 层
- **跨领域调用**：通过事件总线（轻量级）或直接调用，避免循环依赖

### 3.4 基础设施层（Infrastructure Layer）

#### 模块 3.4.1 数据持久化

| 项 | 说明 |
|----|------|
| **职责** | 数据库连接管理、ORM、迁移、连接池 |
| **设计要点** | - Repository 接口与实现分离（方便单测）<br>- 数据库迁移有版本管理<br>- 长事务与短事务分离 |

| **关键决策** | 一期不强制引入 Redis；可用进程内 LRU 缓存兜底，二期再上 Redis |

#### 模块 3.4.3 配置中心

| 项 | 说明 |

| **关键决策** | - **配置文件 + 数据库双层**：默认配置走文件，覆盖配置走数据库<br>- **热更新**：监听配置变更，触发回调<br>- **审计**：每次配置变更记录操作人、时间、原因 |
| **日志** | 每次配置变更、配置生效、配置推送失败 |

#### 模块 3.4.4 进程管理（健康检查 / 启停）

| 项 | 说明 |
|----|------|

| **核心能力** | - 注册 Windows Service（NSSM 包装）<br>- 心跳 / 健康检查端点<br>- 优雅关闭（处理完当前事件再退出） |
| **日志** | 启动、停止、优雅关闭进度、心跳 |

## 四、日志系统设计 ⭐ 重点

### 4.1 日志分级

| 级别 | 用途 | 样例 |
|------|------|------|
| **DEBUG** | 详细诊断信息，仅开发时开启 | 每帧处理耗时、每条算法事件详情 |
| **INFO** | 关键业务流程节点 | 服务启动、配置生效、算法任务启停、报表生成完成 |
| **WARNING** | 异常但不影响主流程 | 摄像头断线自动重连、算法事件解析异常（已容错）、缓存命中失败 |
| **ERROR** | 影响某个功能但服务仍可运行 | 工时计算失败、数据库写入失败、报表导出失败 |
| **CRITICAL** | 系统级故障，必须立即处理 | 数据库连接断开、算法侧长时间无响应、服务 OOM |

### 4.2 日志分层

```
timetrack/
├── logs/
│   ├── app/
│   │   ├── app.log                  # 全量 INFO+（按天滚动）
│   │   ├── app.error.log            # ERROR+（按天滚动）
│   │   └── app.log.2026-09-05       # 历史滚动文件
│   ├── modules/
│   │   ├── algo_adapter.log         # 算法适配层
│   │   ├── camera.log               # 摄像头适配层
│   │   ├── event_orchestrator.log   # 事件编排
│   │   ├── workhour.log             # 工时计算
│   │   ├── report.log               # 报表
│   │   └── system.log               # 系统监控
│   ├── audit/
│   │   ├── config_change.log        # 配置变更审计
│   │   ├── workhour_correction.log  # 工时人工修正审计
│   │   └── data_export.log          # 数据导出审计
│   └── archive/
│       └── 2026-09/                 # 每月归档压缩包
└── log_config.yaml                  # 日志配置
```

**设计要点**：
- **按模块拆分日志文件**：便于定位问题（"算法事件丢了"只看 algo_adapter.log）
- **按级别拆分**：ERROR 单独文件，方便监控告警（脚本扫描即可）
- **审计日志独立**：配置变更、人工修正、数据导出必须有审计留痕（甲方合规要求）
- **按天滚动 + 按月归档**：保留周期可配置（建议 30 天热 + 1 年归档）

### 4.3 日志格式（结构化 JSON）

```json
{
  "ts": "2026-09-05T18:30:15.123+08:00",
  "level": "INFO",
  "module": "event_orchestrator",
  "event": "personnel_event_received",
  "trace_id": "abc123",                    // 全链路追踪 ID
  "camera_id": "cam_01",
  "global_id": "g_0042",
  "zone_id": "tire_position_01",
  "event_type": "enter",
  "latency_ms": 45,
  "message": "Personnel event processed",
  "context": {
    "frame_seq": 123456,
    "confidence": 0.93
  }
}
```

**每个关键事件都要包含的字段**：
- `ts`：时间戳（毫秒级）
- `level`：日志级别
- `module`：模块名（与文件名一致）
- `event`：事件名（短横线命名，如 `personnel_event_received`）
- `trace_id`：关联同一次业务操作的多个日志
- `message`：人类可读的描述

### 4.4 关键日志事件清单（必须有的）

| 模块 | 关键 event 名 | 触发时机 |
|------|--------------|----------|
| **服务生命周期** | `service_start`, `service_stop`, `service_heartbeat` | 启动/停止/每分钟 |
| **配置中心** | `config_loaded`, `config_changed`, `config_push_failed` | 配置变更 |
| **摄像头** | `camera_connected`, `camera_disconnected`, `camera_reconnect`, `stream_started`, `stream_stopped` | 摄像头状态变化 |
| **算法适配** | `algo_task_started`, `algo_task_stopped`, `algo_event_received`, `algo_event_invalid`, `algo_heartbeat_lost` | 算法交互 |
| **事件编排** | `event_received`, `event_dedup`, `event_persisted`, `event_published`, `event_dropped` | 每条算法事件 |
| **工时计算** | `workhour_computed`, `workhour_rule_applied`, `workhour_corrected`, `workhour_recomputed` | 工时变化 |
| **报表** | `report_task_created`, `report_task_started`, `report_task_completed`, `report_task_failed` | 报表任务 |
| **系统监控** | `health_check_ok`, `health_check_degraded`, `health_check_failed`, `alert_triggered` | 监控 |

> 这些事件名是**契约**——前端可以基于这些事件名做展示（虽然不需要，但未来二期做事件总线时会用到）。

### 4.5 日志查询工具（给甲方/运维用）

**一期交付**：一个简易的"日志查询"前端页面或 CLI 工具

### 5.4 算法升级的兼容性约束（提前约定）

> **算法侧后续升级模型/算法时，必须遵守的契约**：
> 1. JSON Schema **只加字段、不删字段**（删除字段必须提前 1 个版本通知）
> 2. 新增算法能力（如工种识别）通过 `event.features` 字段携带，不影响现有字段
> 3. 算法侧提供灰度能力（旧模型 / 新模型可同时运行）
> 4. 算法侧独立部署、独立升级，**后端无需重启**

## 八、模块划分合理性自检 ⭐

> 按你的要求，下面是从**设计角度**对模块划分的合理性检查。

### 8.1 ✅ 划分合理之处

| 设计点 | 合理性 |
|--------|--------|
| **算法侧通过适配层接入** | 算法不是你做，适配层让你不用关心算法侧的实现细节，未来算法侧升级不影响业务层 |
| **接入层 / 业务编排层 / 领域层 / 基础设施层 四层** | 单人项目也能保持边界，避免"一个文件塞所有逻辑" |
| **事件编排服务做去重、编排、推送** | 业务层有清晰的"主流程"，不与算法侧耦合 |
| **领域层独立** | 业务规则集中在一处，未来工时规则改动不影响上下游 |
| **基础设施层** | 数据库、缓存、日志、配置是"横切关注点"，独立成层便于统一处理 |
| **日志按模块 + 按级别 + 按审计 三维拆分** | 出问题时能快速定位模块，也满足甲方合规留痕 |
| **配置外置 + 热更新** | 摄像头点位变化、工时规则调整不动代码 |
| **算法契约提前约定** | 与算法工程师有明确的"接口合同"，避免后期扯皮 |

### 8.2 ⚠️ 需要警惕的过度设计

| 项 | 风险 | 对策 |
|----|------|------|
| **四层架构对单人项目偏重** | 容易陷入"为分层而分层"，增加文件数和阅读成本 | 一期可简化为 3 层（合并接入层+编排层），业务量大了再拆 |
| **Repository 模式对单人也偏重** | ORM 已经够用，再包一层浪费时间 | 简单 CRUD 直接用 ORM，复杂聚合才用 Repository |
| **事件总线对一期过早** | 一期一个进程，不需要消息队列 | 一期用进程内事件回调即可，二期再上 Redis/MQ |
| **审计日志可能过细** | 配置变更审计可考虑简化 | 一期只审计 3 类：配置变更、人工修正、数据导出 |
| **审计日志可能不够细** | 一些"敏感操作"未覆盖 | 列出甲方要求的审计清单（建议人工修正、配置变更、数据导出、对接外部系统） |

### 8.3 模块依赖图（避免循环依赖）

```
       [接入层]
       /   |   \
      ↓    ↓    ↓
   [业务编排层]
       /   |   \
      ↓    ↓    ↓
    [领域层]
       /   |   \
      ↓    ↓    ↓
   [基础设施层]

✅ 单向依赖，无循环
⚠️ 领域层不应依赖业务编排层（业务编排层反过来依赖领域层）
⚠️ 基础设施层不依赖任何上层
```

### 8.4 关键边界判断（容易模糊的地方）

| 模糊点 | 划分原则 |
|--------|----------|
| **工时计算放在业务编排层还是领域层？** | 工时规则（有效判定、班次计算）放**领域层**，工时累计调度（定时器、推送）放**业务编排层** |
| **去重逻辑放在哪？** | 算法侧跨摄像头去重由算法侧做；后端"业务级去重"放**业务编排层**（流水噪声过滤） |
| **配置变更审计** | **基础设施层**（配置中心自带审计） |
| **工时人工修正审计** | **业务编排层**（业务事件） |
| **算法侧日志由谁打？** | **算法适配层**打（接收、解析、入队的日志），算法侧自身的日志由算法侧自己负责 |
| **摄像头断线告警** | 由**接入层**触发，**系统监控服务**汇总后告警 |
