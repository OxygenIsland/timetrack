# 🔴 错误码体系规范（一期契约）

> **目标**：前后端所有异常和错误都有统一编码、分类、可定位、可追溯。
> **适用范围**：前后端所有模块的所有错误（包括前端 UI 异常、后端业务异常、第三方对接异常）。
> **错误码唯一来源**：本文档。任何代码不允许硬编码错误码字符串，必须引用此规范。
> **关联文档**：`后端架构设计文档.md`、`技术路线设计文档.md`

---

## 一、错误码设计原则

| 原则 | 含义 | 为什么重要 |
|------|------|-----------|
| **唯一性** | 一个错误对应唯一编码 | 排查问题时可直接定位 |
| **可分类** | 从编码就能看出错误大类、来源、严重度 | 日志聚合、告警分级 |
| **可定位** | 错误码能告诉开发"哪里出错、为什么出错" | 甲方报障时直接说"出了 E-CAM-001"，你知道查哪里 |
| **稳定性** | 错误码不随版本变化而变化（除非错误本身被废弃） | 文档、运维脚本、前端 i18n 都依赖错误码 |
| **可追溯** | 每个错误都带 trace_id，能串起前后端日志 | 现场调试 30 秒定位 |
| **人话 message** | 给用户的 message 必须说人话；技术细节在 details 里 | 前端直接展示 message 给用户 |

## 二、错误码结构

### 2.1 编码格式

```
E-{模块}-{子模块}-{序号}

示例：
E-CAM-001      ← 摄像头模块 - 离线
E-ALG-003      ← 算法模块 - 心跳超时
E-WH-002       ← 工时模块 - 规则冲突
E-DB-001       ← 数据库模块 - 连接失败
```

**位数说明**：
- `E-` 前缀：固定，标识这是一个错误码（vs 正常返回）
- `{模块}`：3 字母大写，标识错误来源系统（CAM / ALG / DB / ...）
- `{子模块}`：3 位数字，标识子模块（001 = 通用，002 = 离线，003 = 鉴权...）
- `{序号}`：3 位数字，同一子模块下的具体错误序号

### 2.2 模块编号（已规划）

| 编码 | 模块 | 说明 |
|------|------|------|
| `SYS` | 系统级 | 全局通用错误 |
| `CAM` | 摄像头 | 摄像头接入、流处理 |
| `ALG` | 算法 | 算法适配层 |
| `NVR` | NVR | 历史录像接入 |
| `EVT` | 事件编排 | 实时事件处理 |
| `WH` | 工时 | 工时计算 |
| `RPT` | 报表 | 报表生成 |
| `CFG` | 配置 | 配置中心 |
| `AUTH` | 鉴权 | 登录、权限 |
| `WS` | WebSocket | 实时通信 |
| `API` | API | 通用 API |
| `DB` | 数据库 | 持久化 |
| `EXT` | 外部对接 | 第三方系统 |
| `FE` | 前端 | 前端 UI / 组件异常 |

## 三、错误响应统一格式

### 3.1 HTTP 错误响应（REST API）

```json
{
  "code": "E-CAM-001",
  "http_status": 503,
  "message": "摄像头 cam_01 当前离线，请检查网络连接",
  "message_en": "Camera cam_01 is offline, please check network connection",
  "trace_id": "abc123def456",
  "timestamp": "2026-09-05T18:30:15+08:00",
  "path": "/api/v1/cameras/cam_01/status",
  "details": {
    "camera_id": "cam_01",
    "last_seen": "2026-09-05T18:25:00+08:00",
    "retry_count": 3
  },
  "suggestion": "请检查摄像头电源和网络，或联系运维人员"
}
```

**字段说明**：

| 字段 | 必填 | 用途 |
|------|------|------|
| `code` | ✅ | 错误码（本文档定义） |
| `http_status` | ✅ | HTTP 状态码 |
| `message` | ✅ | 中文用户提示（前端直接展示） |
| `message_en` | ❌ | 英文提示（国际化备用） |
| `trace_id` | ✅ | 全链路追踪 ID |
| `timestamp` | ✅ | 服务端时间戳 |
| `path` | ❌ | API 路径 |
| `details` | ❌ | 技术详情（开发排查用） |
| `suggestion` | ❌ | 给用户的解决建议 |

### 3.2 WebSocket 错误消息

```json
{
  "type": "error",
  "code": "E-WS-001",
  "message": "WebSocket 连接断开",
  "trace_id": "abc123",
  "timestamp": "2026-09-05T18:30:15+08:00",
  "details": {
    "channel": "personnel_realtime",
    "reason": "connection_lost"
  }
}
```

### 3.3 业务成功响应（用于校验）

业务成功不应返回 error，但仍可使用统一响应壳：

```json
{
  "code": "OK",
  "http_status": 200,
  "data": { ... },
  "trace_id": "abc123",
  "timestamp": "2026-09-05T18:30:15+08:00"
}
```

## 四、错误码详细定义

> 格式说明：
> - **错误码**：唯一标识
> - **HTTP 状态**：HTTP 返回码（WebSocket 不适用）
> - **级别**：FATAL / ERROR / WARNING / INFO
> - **触发条件**：什么场景下抛出
> - **用户提示**：前端展示给用户的话
> - **建议操作**：用户/运维应该怎么做
> - **日志级别**：后端打什么级别日志

## 五、错误码使用规范

### 5.1 后端实现（FastAPI 示例）

```python
# app/errors/exceptions.py
class BizException(Exception):
    """业务异常基类"""
    def __init__(self, code: str, message: str, details: dict = None, http_status: int = 500):
        self.code = code
        self.message = message
        self.details = details or {}
        self.http_status = http_status
        super().__init__(message)


class CameraOfflineException(BizException):
    def __init__(self, camera_id: str, last_seen: str):
        super().__init__(
            code="E-CAM-001",
            message=f"摄像头 {camera_id} 当前离线，请检查网络连接",
            details={"camera_id": camera_id, "last_seen": last_seen},
            http_status=503,
        )
```

```python
# app/errors/handler.py
@app.exception_handler(BizException)
async def biz_exception_handler(request: Request, exc: BizException):
    trace_id = getattr(request.state, "trace_id", str(uuid4()))
    logger.error(
        f"biz_exception",
        extra={
            "event": "biz_exception",
            "code": exc.code,
            "trace_id": trace_id,
            "path": request.url.path,
        }
    )
    return JSONResponse(
        status_code=exc.http_status,
        content={
            "code": exc.code,
            "http_status": exc.http_status,
            "message": exc.message,
            "trace_id": trace_id,
            "timestamp": now_iso(),
            "path": request.url.path,
            "details": exc.details,
        }
    )
```

### 5.2 前端实现（React + TS 示例）

```typescript
// src/api/error.ts
export interface ApiError {
  code: string;
  http_status: number;
  message: string;
  message_en?: string;
  trace_id: string;
  timestamp: string;
  path?: string;
  details?: Record<string, any>;
  suggestion?: string;
}

// 错误码常量定义（与后端文档同步）
export const ErrorCodes = {
  CAM_OFFLINE: 'E-CAM-001',
  ALG_UNAVAILABLE: 'E-ALG-001',
  WH_INVALID_RULE: 'E-WH-003',
  // ... 更多
} as const;

// 统一错误处理
export function handleApiError(error: ApiError) {
  console.error(`[${error.code}] ${error.message}`, error.details);

  // 根据错误码做差异化处理
  switch (error.code) {
    case ErrorCodes.AUTH_TOKEN_EXPIRED:
      // 跳转登录
      navigateToLogin();
      break;
    case ErrorCodes.CAM_OFFLINE:
      // 显示摄像头离线提示
      showCameraOfflineToast(error.details.camera_id);
      break;
    // ...
  }

  // 默认全局提示
  showToast({
    type: 'error',
    message: error.message,
    suggestion: error.suggestion,
    duration: getDurationByLevel(error.code),
  });
}
```

### 5.3 错误码与日志级别的映射

| 错误码级别 | 日志级别 | 是否触发告警 |
|-----------|---------|-------------|
| FATAL | CRITICAL/ERROR | ✅ 立即告警 |
| ERROR | ERROR | ⚠️ 阈值告警（如 1 分钟内 ≥10 次） |
| WARNING | WARNING | ❌ 仅记录 |
| INFO | INFO | ❌ 仅记录 |

## 六、全链路追踪（trace_id）

### 6.1 什么是 trace_id

每个请求（HTTP / WebSocket / 算法事件）都有一个**唯一 trace_id**，贯穿整个调用链，用于串起前后端日志。

### 6.2 trace_id 生成与传递

```
前端发起请求
  → 生成 trace_id（前端 UUID）
  → HTTP Header `X-Trace-Id` 传给后端
  → 后端使用此 trace_id 处理
  → 后端响应中携带 trace_id
  → 前端拿到 trace_id
  → 用户报障时报出 trace_id → 运维直接定位日志
```

### 6.3 WebSocket trace_id

WebSocket 连接建立时，前端发送 `{type: "init", trace_id: "xxx"}`，后端使用该 trace_id 作为本次连接的基础 trace_id。

### 6.4 算法事件 trace_id

算法事件本身有 `event_id`，后端将其作为 trace_id 处理。

## 八、错误码扩展规则

### 8.1 新增错误码流程

1. 在本规范文档中**新增**错误码定义（评审）
2. 前端常量文件 `ErrorCodes` 同步新增
3. 后端异常类中新增对应异常
4. 通知前端、后端、算法侧所有人员

### 8.2 废弃错误码流程

1. 在错误码后加 `【废弃于 vX.X】` 标记
2. 保留至少 2 个版本（方便历史日志查询）
3. 通知所有相关人员

### 8.3 错误码不允许

- ❌ **不允许**用魔法数字/字符串（如 `"1001"`, `"AUTH_FAILED"`）
- ❌ **不允许**在代码里硬编码错误消息字符串（必须引用本规范）
- ❌ **不允许**错误码含义改变（如 E-CAM-001 今天表示"离线"，明天表示"超时"）
- ❌ **不允许**错误码被复用（即使模块废弃了，错误码也要保留）

## 九、错误码 - 日志 - 告警 三者关系

```
[业务异常]
    │
    ├─→ [抛出 BizException(code, message)]
    │       │
    │       ├─→ [全局异常处理器]
    │       │       │
    │       │       ├─→ [返回 HTTP 响应 {code, message, trace_id}]
    │       │       │       │
    │       │       │       └─→ [前端 handleApiError]
    │       │       │               │
    │       │       │               ├─→ [toast 提示用户]
    │       │       │               └─→ [console.error 记录]
    │       │       │
    │       │       └─→ [写日志: logger.error(event="biz_exception", code, trace_id)]
    │       │               │
    │       │               └─→ [告警脚本扫描]
    │       │                       │
    │       │                       └─→ [触发阈值告警]
    │       │
    │       └─→ [trace_id 串联同请求的所有日志]
```
